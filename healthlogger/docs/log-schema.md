# HealthLogger Log Schema

## 1. Purpose

This document describes the JSONL formats used by HealthLogger.

HealthLogger uses JSON Lines (JSONL) for storing health events and for producing structured logs to standard output.

Each JSONL record is a complete JSON object stored on a single line.

The JSONL outputs serve different purposes:

* By default, `data/events.jsonl` stores valid health events. The event-store path can be overridden using the `--store` command-line option or the `HEALTHLOGGER_STORE` environment variable.
* Standard output contains structured operational logs for processed events.

Rejected HTTP submissions are stored separately in `data/rejected-events.jsonl`.

Unless otherwise stated, references to `data/events.jsonl` and `data/rejected-events.jsonl` in this document describe the default storage paths.

## 2. Valid Event Storage

By default, valid events are stored in `data/events.jsonl`. Each valid event occupies one line in the file.

### 2.1 Configuring the event-store path

The event-store path can be changed using the `--store` command-line option or the `HEALTHLOGGER_STORE` environment variable.

If both `--store` and `HEALTHLOGGER_STORE` are provided, the `--store` command-line option takes precedence.

Rejected HTTP submissions are stored separately in a file named `rejected-events.jsonl` in the same directory as the configured event store. By default, this file is `data/rejected-events.jsonl`.

For example, if the event-store path is `custom/events.jsonl`, rejected HTTP submissions are stored in `custom/rejected-events.jsonl`.

Example:

```json
{"service":"payments-api","status":"ok","timestamp":"2026-09-29T10:00:00Z"}
```

The fields in the event are determined by the client specification in:

```text
config/client-spec.json
```

The current required fields are:

* `service`
* `status`
* `timestamp`

Additional fields may be included in an event. The current validation checks required fields and allowed status values.

### JSONL rule

The file follows the JSON Lines format:

```text
one JSON object
one line

one JSON object
one line

one JSON object
one line
```

Each line can therefore be processed independently.

## 3. Rejected Event Storage

Rejected submissions are stored separately from valid events in:

```text
data/rejected-events.jsonl
```

A rejected record contains:

* `timestamp` - when the rejection was recorded
* `input` - the rejected submission's input. For HTTP requests exceeding 1 MiB, this is the bounded placeholder `[request body omitted: exceeds maximum size]` instead of the full request body.
* `reason` - why the submission was rejected

Example:

```json
{"timestamp":"2026-10-01T14:05:31Z","input":{"status":"ok","service":"payments-api"},"reason":"missing required field: timestamp"}
```

Malformed JSON is also recorded. The rejection reason begins with `malformed JSON` and may include additional details from the JSON parser.

Example (the parser detail is illustrative):

```json
{
  "timestamp":"2026-10-01T14:13:55Z",
  "input":"{\"service\":\"payments-api\",\"status\":",
  "reason":"malformed JSON: [parser error details]"
}
```


Rejected records are not written to `data/events.jsonl`.

## 4. Structured Standard Output Log

HealthLogger also produces structured JSON logs on standard output.

The structured logging implementation is provided by:

```text
src/main/java/com/genkey/healthlogger/StructuredLogger.java
```

A successful event produces a log with three main fields:

```json
{
  "ts": "2026-10-01T10:30:03Z",
  "severity": "info",
  "event": {
    "service": "payments-api",
    "status": "ok",
    "timestamp": "2026-09-29T10:00:00Z"
  }
}
```

### Fields

#### `ts`

The `ts` field contains the time at which the structured log entry was created.

Example:

```text
"ts": "2026-10-01T10:30:03Z"
```

It is generated by HealthLogger using the current time.

---

#### `severity`

The `severity` field describes the severity associated with the event.

Its value is determined from the `severityMap` in:

```text
config/client-spec.json
```

Current mappings are:

| Status     | Severity |
| ---------- | -------- |
| `ok`       | `info`   |
| `degraded` | `warn`   |
| `down`     | `error`  |

This means the logging severity is client-spec driven rather than hardcoded into the logger.

---

#### `event`

The `event` field contains the original health event fields.

Example:

```json
"event": {
  "service": "payments-api",
  "status": "ok",
  "timestamp": "2026-09-29T10:00:00Z"
}
```

The event fields come from the submitted JSON and are not represented by a fixed Java event schema.

---

## 5. Difference Between Event Storage and Structured Logs

The valid event store and the standard output log have different purposes.

### Event store

```text
data/events.jsonl
```

Contains the actual health events:

```json
{"service":"payments-api","status":"ok","timestamp":"2026-09-29T10:00:00Z"}
```

### Structured stdout log

Contains information about the event and its logging context:

```json
{
  "ts":"2026-10-01T10:30:03Z",
  "severity":"info",
  "event":{
    "service":"payments-api",
    "status":"ok",
    "timestamp":"2026-09-29T10:00:00Z"
  }
}
```

Therefore:

```text
events.jsonl
    ↓
actual stored event

stdout log
    ↓
structured operational log
```

The two formats should not be treated as interchangeable.

 ## 6. HTTP Processing Flow

For an HTTP event submission, the data flow is:

```text
POST /events
      |
      v
Read request body (maximum 1 MiB)
      |
      v
Body exceeds 1 MiB?
      |
      +--------------------------+
      |                          |
     Yes                         No
      |                          |
      v                          v
Store bounded placeholder    Parse JSON
in RejectedEventStore            |
      |                          +----------------------+
      v                          |                      |
Rejection saved?                 v                      v
      |                     Malformed JSON         Valid JSON
  +---+---+                      |                      |
  |       |                      v                      v
 Yes      No              Record rejection          Validate
  |       |                      |                      |
  v       v                      v              +-------+-------+
HTTP    HTTP                 Rejection saved?    |               |
413     500                       |              v               v
                              +---+---+        Invalid          Valid
                              |       |           |               |
                             Yes      No          v               v
                              |       |     RejectedEventStore  JsonlStore
                              v       v                           |
                           HTTP 400 HTTP 500                       v
                                                            StructuredLogger
                                                                   |
                                                                   v
                                                                 stdout
```

For oversized requests, the stored `input` is the bounded placeholder `[request body omitted: exceeds maximum size]`, rather than the full request body. If recording the oversized request fails, the server returns HTTP `500` instead of `413`.

Malformed JSON returns HTTP `400` when its rejection record is saved successfully, or HTTP `500` if that write fails.

Valid events are stored in `events.jsonl` and also produce a structured stdout log. Invalid or malformed submissions are recorded separately in `rejected-events.jsonl`.

## 7. JSONL Design Rules

HealthLogger follows these rules for JSONL data:

1. Each record is a complete JSON object.
2. Each record occupies one line.
3. Valid events are stored in `data/events.jsonl`.
4. Rejected submissions are stored in `data/rejected-events.jsonl`.
5. Structured logs are written to standard output.
6. Event field names are driven by `config/client-spec.json`.
7. Query output should not be mixed with structured stdout logging.

## 8. Example End-to-End Output

Given the following event:

```json
{
  "service": "payments-api",
  "status": "ok",
  "timestamp": "2026-09-29T10:00:00Z"
}
```

The valid event store contains:

```text
data/events.jsonl
```

```json
{"service":"payments-api","status":"ok","timestamp":"2026-09-29T10:00:00Z"}
```

The structured stdout log contains:

```json
{"ts":"2026-10-01T10:30:03Z","severity":"info","event":{"service":"payments-api","status":"ok","timestamp":"2026-09-29T10:00:00Z"}}
```

If the same submission is missing the required `timestamp` field, it is rejected and recorded in:

```text
data/rejected-events.jsonl
```

Example:

```json
{"timestamp":"2026-10-01T14:05:31Z","input":{"service":"payments-api","status":"ok"},"reason":"missing required field: timestamp"}
```

## 9. Summary

HealthLogger uses separate JSONL representations for different purposes:

```text
data/events.jsonl
        |
        +--> Valid health events


data/rejected-events.jsonl
        |
        +--> Rejected submissions and reasons


stdout
        |
        +--> Structured operational logs
             - ts
             - severity
             - event
```

This separation keeps stored health events, rejected submissions, and operational logging clearly defined and independently usable.
